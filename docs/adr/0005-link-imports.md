# 5. Links are fetched by a pinned yt-dlp in a child process, from eight sites only

People asked to paste a YouTube or Instagram link instead of saving the file first. Writing site readers by hand was rejected: sites change every few weeks and yt-dlp already follows them. Running yt-dlp as it comes was rejected too, because by default it reads config files and plugins, can use a browser's cookies, fetches a challenge solver from the internet, hands some streams to ffmpeg, and merges files with its own post-processors. sukoon pins yt-dlp and `yt-dlp-ejs` (the YouTube solver, run in the Node.js that building the interface already needs) in `uv.lock`, with a floor rather than an exact version in `pyproject.toml` so that one command can update them, and calls the API with all of that turned off: no config, no cookies, no plugins, no remote components, no ffmpeg of its own, no post-processors, no playlists, and only the extractors of the pasted site. A link must be `https` to one of twelve host names; everything else is refused before any request. The download runs in a spawned child process, like separation, so a hang or a crash in a site reader cannot reach the server; Cancel kills it, and ten minutes without progress fails the job. Video and audio arrive as separate parts, and each part goes through the same check an upload gets before sukoon's own ffmpeg joins them, so a link can put nothing on disk that an upload could not. The only new network traffic is to the pasted site and its media servers, and only when someone pastes. The cost is upkeep: when a site changes, links from it fail until yt-dlp is updated by hand, so `sukoon doctor` warns at 60 days and every failure that looks like an old reader says how to update. Some sites refuse signed-out requests (Vimeo, Instagram's sound, TikTok without browser impersonation); sukoon says so and does not sign in. Revisit if a site the users need can only be read with an account, or if browser impersonation becomes worth its extra dependency.
